# Plan de corrección — auditoría UX + QA de somosnortex.com

**Fuente:** auditoría entregada por el usuario, fechada 2026-09-22, cuenta demo «Pulpería La Demo». **Estado de este documento:** plan redactado inicialmente en `codex/caja-nica-retention` y trasladado al candidato sobre `main`; la evidencia ejecutada de este último vive en `AVANCE_CORRECCION_AUDITORIA_UX_QA_2026-09-22.md`. La auditoría observó producción con navegador; comparar versión/SHA servido, API y datos antes de atribuir un defecto a este código.

## Regla de ejecución

1. Preservar el checkout y sus cambios. Para corregir código, preparar candidato aislado que incluya la base exacta que se quiere probar; registrar SHA, diff y procedencia. Leer `AGENTS.md`, `CLAUDE.md` y la skill `.claude/skills/nortex-feature/SKILL.md` en ese candidato.
2. Reproducir cada caso con datos sintéticos en tenant descartable y conservar el antes/después del mismo escenario. Las capturas de la auditoría son evidencia de observación, no prueba de la causa ni del estado del candidato.
3. Una prueba ejecutable contra la función/ruta real debe fallar antes de cada reparación relevante. Dinero, stock y caja requieren HTTP + MySQL 8 local con `npm run test:integration:required`; verificar auditoría, asiento, Kardex, reintento y aislamiento por tenant donde correspondan. Ejecutar además Prisma generate, TypeScript, Vitest dirigido, diseño y build; usar `NORTEX_CI_MUTATION=1` si cambia lógica monetaria.
4. Registrar por hallazgo: candidato/SHA, reproducción, cambio, pruebas, captura desktop y móvil cuando aplique, estado **demostrado / defecto reproducido / riesgo por validar / no probado**. CI del SHA, staging y producción son compuertas separadas. No tocar la cuenta demo ni sus datos para probar reparaciones locales.

## Orden de entregas y evidencia esperada

1. **Diagnóstico P0:** comparación producción/candidato, reproducción local y expediente contable/caja. Salida: causa demostrada o riesgo por validar con trazas; no modificar datos reales.
2. **Reparaciones financieras en lotes pequeños:** #11, #12, #3/U-03 y #2 por separado. Cada lote: prueba roja, parche, integración MySQL/HTTP, revisión de tenant/roles, antes/después y límites.
3. **Cobro y operación:** U-01/U-02, #1, #5/#14/U-04. Verificar ventas y compras completas y conservación del carrito/borrador.
4. **Archivo de maestros:** contrato por agregado, migración aditiva cuando haga falta, backend, UI y QA histórica. Aislar esta entrega de las correcciones de dinero.
5. **Recuperación y pulido:** U-05/U-06/U-07/U-09, luego lenguaje L1–L26/U-10. U-08 se inicia tras cerrar su contrato de identidad y permisos.
6. **Promoción:** revisión de diff y QA local del SHA; CI del mismo SHA; staging con smoke de los recorridos; aprobación separada para producción. Después de desplegar, verificar salud y casos sintéticos sin reusar la cuenta auditada para mutaciones.

- #11: saldo no negativo obtenido ocultando, truncando o compensando sin conciliar asientos y stock.
- #12: inferir pérdida de C$ 200 por reinicio sin solicitud, `shiftId`, respuesta y auditoría que la sostengan.
- #2: mostrar canales nuevos que el backend no autoriza o reembolsar dinero no cobrado.
- #3/U-03: mostrar saldo total calculado con estado anterior al abono o confundirlo con la factura.
- #10/#13: borrar físicamente o perder referencias de ventas, compras, CxC, CxP o Kardex.
- Cualquier lote: pruebas omitidas, resultado local atribuido a producción o capturas de otra versión presentadas como evidencia del candidato.
