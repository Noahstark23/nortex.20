## 4. Perfil OAuth propuesto para implementar

Es una decisión de diseño Nortex, no una declaración de compatibilidad ya demostrada.

- Authorization Code, PKCE `S256` obligatorio; nada de implicit, password grant o client credentials para actuar como comerciante.
- Clientes preconfigurados, separados por entorno; sin registro dinámico público en v1.
- Código de 60 segundos y un solo uso; access token opaco de 10 minutos; refresh rotatorio con máximo absoluto de 30 días y 7 días de inactividad. Son valores propuestos, no plazos exigidos por el estándar.
- Códigos/tokens aleatorios mediante CSPRNG, al menos 32 bytes de entropía; persistencia por hash, nunca tokens utilizables en claro en logs o BD. El valor utilizable sólo transita por la respuesta de emisión y la petición autenticada.
- Grant ligado a `userId`, `tenantId`, `clientId`, recurso/audiencia, scopes consentidos y estado. Un grant pertenece a un negocio. Cambiar el negocio exige autorización nueva y pertenencia verificada; no se concede selección multi-tenant inexistente.
- Revalidar usuario activo, pertenencia, rol, grant, cliente y política vigente en cada acceso y antes del efecto transaccional. Ante indisponibilidad de autoridad, fallar cerrado.
- El token externo no entra a `/api/admin`, al POS interno ni al login habitual. No existe conversión a JWT interno ni fallback automático al middleware viejo.
- La revocación marca el grant/familia correspondiente y corta el acceso asociado; deshabilitar usuario o cliente tiene efecto inmediato en solicitudes nuevas. Una operación ya comprometida no se revierte por desconectar el conector.

### 4.1 HTTP y consentimiento

Rutas propuestas: `/.well-known/oauth-authorization-server`, `/oauth/authorize`, `/oauth/authorize/decision`, `/oauth/token`, `/oauth/revoke` y `/api/integrations/muse/v1/*`.

No publicar issuer, callbacks o endpoints de un dominio no decidido. Metadatos sólo de capacidades implementadas; JWKS/ID token/OIDC no son necesarios para el perfil opaco propuesto. Introspección pública y registro dinámico quedan fuera de v1.

El servidor valida cliente, callback exacto, scopes y PKCE antes de redirigir. Un callback inválido nunca recibe códigos ni errores mediante redirect. No aceptar wildcards, fragmentos o redirecciones abiertas. El cliente debe comprobar `state`.

El navegador que abre authorize no lleva por arte de magia el header JWT del login actual. Crear una transacción de autorización temporal: la interfaz confiable de Nortex autentica al usuario y muestra negocio, cliente y permisos; la decisión se vincula a esa transacción y a protección CSRF/browser binding. No transportar JWT interno en URL. Una sesión iniciada y el consentimiento son eventos diferentes.

`/oauth/token` y `/oauth/revoke` usan cuerpos y respuestas del protocolo, parsers acotados y un método de autenticación fijado por cliente; no adivinar Basic/post/none por lo que envía la petición. Respuestas de tokens con `Cache-Control: no-store` y `Pragma: no-cache`. Nada de bearer tokens en query, trazas o analítica. Cookies de transacción con Secure, HttpOnly y política SameSite compatible con el flujo probado.

Errores previstos: `invalid_request`, `invalid_client`, `invalid_grant`, `invalid_scope`; acceso sin token válido: 401/Bearer; scope insuficiente: 403; conflicto de negocio: 409; cuota: 429; dependencia no verificable: 503 sin datos privados. No usar un 404 o timeout como prueba de que una escritura no ocurrió.

### 4.2 Persistencia y carreras

Entidades propuestas: cliente OAuth, transacción de consentimiento, autorización/grant, código de autorización, familia de refresh y tokens de acceso/renovación. Las relaciones conservan tenant y propietario; índices/constraints impiden doble consumo. La migración exacta se especifica con el schema real antes de escribirla.

El canje debe verificar todos los vínculos y consumir el código/emisión de tokens de forma atómica. Con refresh, una transacción consume la generación vigente y emite la siguiente. La reutilización verificada revoca la familia; no crear un segundo refresh válido como tolerancia a carreras. El cliente debe serializar la renovación. Una carrera o respuesta perdida puede requerir reconexión: documentar ese resultado sin fingir recuperación de secretos que sólo se guardaron como hash.

No confiar en hooks independientes de librería sin demostrar el alcance transaccional que comparte lectura, validación, consumo y guardado. El orden de locks se concilia con los servicios existentes y se prueba con concurrencia. Evitar redes/IA dentro de transacciones.

## 5. Scopes y superficie mínima

Autorización efectiva = cliente permitido ∩ consentimiento ∩ scopes del token ∩ rol vigente ∩ capacidad del negocio ∩ acceso al recurso concreto. OWNER tampoco evita el límite del grant. Un token de lectura no escribe porque el usuario sea dueño.

| Perfil funcional | Scopes propuestos | Límite |
|---|---|---|
| Bodega/conteo | `catalog:read`, `inventory:read`, `stockcounts:read`, `stockcounts:capture` | Sin costos/utilidad/RRHH; captura no habilita cierre |
| Ventas | `catalog:read`, `pricing:read`, `inventory:read`, `customers:read`, `sales:read`; luego `sales:prepare`, `sales:commit` | Caja/cartera propia cuando la política lo exija |
| Dueño/gerencia financiera | `reports:sales:read`, `reports:profit:read`, más lecturas consentidas | No otorgar utilidad a todos los roles de reportes |
| Compras posteriores | `purchases:read`, `purchases:prepare`, `purchases:commit` | Compra, recepción y pago son efectos distintos |
| Facturación/cobranza posteriores | `invoices:read`, `receivables:read`, después permisos de emisión/anulación/registro | No ejecutar transferencias bancarias |
| RRHH posterior | `hr:employees:read`, `hr:payroll:read`, luego preparación/finalización | Datos propios requieren relación usuario-empleado verificada |

La matriz es un límite máximo de delegación, no una ampliación de permisos internos. Reservar `stockcounts:close` para otra capacidad aprobada. No implementar scopes futuros como comodines.

v1: capacidades disponibles, búsqueda filtrada, existencias por bodega, conteos autorizados, preparación/revisión/preview de captura y recuperación de comprobante. Un reporte determinista separado podrá distinguir ventas, cobros y utilidad bruta con moneda, período, corte y cobertura. No llamar utilidad neta a ventas menos costo histórico sin gastos completos.

Excluir rutas administrativas, cambios de roles, historial interno indiscriminado, ejecución genérica de runs, carga/extracción documental, aprobación de alias, exportaciones masivas, escrituras RRHH y acceso a secretos. El canal del conector procede del servidor; el cliente no puede elegir `WEB_INTERNAL`.

## 6. Captura confirmada: contrato previo a código

Nuevo tipo propuesto: `STOCK_COUNT_CAPTURE`. No existe en el enum revisado. Reutiliza el patrón, no presupone un adaptador implementado.

Preparar guarda como máximo un borrador auxiliar. Resolver producto/variante, conteo abierto, bodega, unidad y lote cuando el dominio lo exija. Cantidad absoluta por defecto; una sustitución o suma debe describirse explícitamente. No convertir cajas a unidades sin catálogo.

Preview genera resumen determinista y vincula propuesta, versión, actor, grant/cliente, tenant, conteo, producto, cantidad y vencimiento. El modelo puede solicitar preparar y mostrar preview; no dispone de una llamada genérica para confirmar efectos. Confirmación requiere una interacción confiable fuera de la autoridad del modelo, ligada a esa versión. `confirmed: true`, una transcripción o devolver un nonce al modelo no prueban aprobación humana.

El adaptador de confirmación sólo acepta referencia, versión y clave idempotente, junto con la evidencia del canal confiable que se defina; no cantidades nuevas. Revalidar recursos y permisos antes de guardar. Efecto, auditoría y comprobante son atómicos. Clave repetida/mismo payload recupera resultado; misma clave/otro payload rechaza. Capturar no cierra inventario, no hace ajustes y no crea asientos.

Revisión de datos, expiración o cambio relevante invalida la aprobación. Ante timeout conservar identidad y consultar comprobante. Un conflicto de saldo conserva el recuento exigido por el dominio. La demo no se anuncia 100% voz hasta verificar realmente el mecanismo de aprobación del proveedor; sin él se mantiene una aprobación autenticada de Nortex, no un bypass.

## 7. Motor OAuth: evaluación inicial

Candidato: `@node-oauth/oauth2-server`. Se consultó documentación identificada como 5.1.0, no se verificó ni instaló una versión de paquete y no se afirma que sea la última.

La [documentación de PKCE](https://node-oauthoauth2-server.readthedocs.io/en/master/misc/pkce.html) describe integración con authorization code y conservación de `codeChallenge`/`codeChallengeMethod` mediante el modelo. El [contrato de modelo](https://node-oauthoauth2-server.readthedocs.io/en/master/model/spec.html) expone get/save/revoke de credenciales y generación de tokens.

Evaluación: candidato razonable para el protocolo; no reemplaza consentimiento, tenant, autorización por recurso, revocación de grant, redacción ni detección transaccional de replay. El backend debe exigir S256 incluso cuando una librería permita otros modos. Guardar hash y reconstruir el objeto esperado con el token presentado no exige almacenar el secreto en claro. Deshabilitar atributos extendidos que filtren datos internos.

Antes de adoptar: fijar versión/resolución en npm lockfile, revisar licencia/advisories, probar Node canónico + ESM + Express 5, medir transacciones/hooks de refresh y códigos con dos peticiones simultáneas, y pruebas de consumo fallido. No extender ni improvisar criptografía para cubrir una incompatibilidad. Si no permite un modelo transaccional seguro, registrar un ADR de alternativa; no ocultar el problema tras hooks que sólo pasan pruebas secuenciales.
